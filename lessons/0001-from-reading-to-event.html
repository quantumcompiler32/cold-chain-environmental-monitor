Cold-chain event pipeline · Lesson 1

From a source reading to a publishable event

Win for this lesson: you can explain what the generator does, what it does not do, and why event_id, event_time, and run_id exist.

The first boundary

This demo uses a CSV as a reproducible stand-in for a sensor. The generator reads a temperature value, converts Fahrenheit to Celsius when needed, applies a named scenario such as normal or warning, classifies it against the vaccine’s storage range, and packages the result as JSON.

CSV guidance → generator transforms one reading → JSON event → MQTT topic devices/temperature

The CSV is guidance, not the authoritative live clock. At generation time, the program creates event_time. That distinction matters: an old source measurement can still produce a new simulated event.

Three identities to keep separate

  • event_id: identity of one reading/event. It is a UUID and later makes duplicate delivery safe.
  • run_id: identity of one generator invocation. Many events can share it, which helps diagnostics.
  • event_time: when the event was created. Later stages add received_at and stored_at.

What the generator guarantees

It produces a contract-shaped message with device, vaccine, scenario, measurement, uncertainty, and status fields. It then publishes the JSON to MQTT. It does not write the dashboard, validate database consistency, or decide whether stock is released or quarantined.
