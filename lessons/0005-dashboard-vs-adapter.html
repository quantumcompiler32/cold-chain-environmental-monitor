Cold-chain event pipeline · Lesson 5

Dashboard versus dashboard adapter

Win for this lesson: you can identify where data is retrieved, transformed, and displayed.

PostgreSQL → dashboard adapter (:8787) → JSON/SSE contract → dashboard frontend (:8766) → operator

The dashboard adapter

The adapter is backend/dashboard_bridge.py. It is a backend service. It connects to PostgreSQL using read-only transactions, queries committed vaccine events, maps database rows into a stable event shape, calculates analytics summaries, and exposes HTTP endpoints and SSE.

It does not draw charts, choose CSS, or decide what a button looks like. Its job is translation:

database-shaped row → browser-friendly JSON

It is read-only. The adapter does not insert, update, or delete event records. It does not start the generator, subscribe to MQTT, or change vaccine disposition. Its PostgreSQL connections use read-only transactions, so the adapter can inspect evidence without mutating the source of truth.

Who writes to PostgreSQL?

The temperature subscriber is the event writer. After validating and deriving state, it writes both telemetry_logs and vaccine_temperature_events in one transaction. PostgreSQL stores the committed result. The adapter only reads that result.

This gives the pipeline a clear direction:

generator → MQTT → subscriber → PostgreSQL → adapter → browser

The arrow direction matters. The dashboard is downstream of persistence; it is not another writer competing with the subscriber.

Adapter permissions in plain language

Think of the adapter as a librarian, not an editor. It can search the committed records, select fields, filter them, count them, and hand the results to the browser. It cannot rewrite the records or create a new event. The subscriber is the editor that accepts and stores events.

When the adapter receives a database notification, PostgreSQL has already committed the rows. The adapter does not trust the notification as the data itself; it uses the event ID as a lookup key, performs a fresh read, and then sends the complete result to the browser.

The dashboard

The dashboard is the frontend in frontend/. HTML defines page structure, CSS defines appearance, and JavaScript calls the adapter and renders tables, cards, filters, alerts, and charts. It is the operator-facing presentation layer.

The dashboard is also read-only with respect to event data. It makes browser requests such as GET /api/events and opens /api/live/stream. It does not connect directly to PostgreSQL, does not hold database credentials, and does not write event rows.

A filter changes what the dashboard asks the adapter to return; it does not change the underlying data. For example, selecting “Pod1” produces an API request with a pod filter. The adapter converts that filter into a safe database query, reads matching committed rows, and returns JSON.

What happens when the page loads?

  1. The browser requests HTML, CSS, and JavaScript from the static frontend server on port 8766.
  2. The JavaScript starts the live watcher or makes a normal API request to the adapter on port 8787.
  3. The adapter opens a read-only PostgreSQL transaction and runs a SELECT.
  4. The adapter maps database values into the frontend contract and serializes them as JSON.
  5. The browser parses the JSON and renders the operator view.

Normal request versus live update

For GET /api/events, the browser asks a question and receives a finished answer. For /api/live/stream, the browser opens a long-lived SSE connection. The adapter waits for PostgreSQL notifications, reads each newly committed event, and pushes updates down that connection. In both cases the adapter reads; the dashboard displays.

Why separate them?

This separation lets the database schema change internally without forcing every browser page to understand the schema. It also keeps browser code away from database credentials and write operations. The adapter can enforce a stable, read-only boundary.

Trace one live event

  1. The subscriber commits the event.
  2. PostgreSQL delivers cold_chain_events notification to the adapter.
  3. The adapter queries the full event by event_id.
  4. The adapter serializes it as an SSE message.
  5. Frontend JavaScript receives the message.
  6. The dashboard updates the operator’s view.
Recall
  1. Which component talks to PostgreSQL?
  2. Which component renders the event as a visible dashboard card or table row?
  3. Why should the browser not connect directly to PostgreSQL?
  4. What does the adapter send across the boundary: raw database rows or a browser-friendly contract?
