Cold-chain event pipeline · Lesson 6

One event, end to end

Win for this lesson: you can follow one event across every component and explain what changes at each boundary.

CSV → generator → MQTT/Mosquitto → subscriber → PostgreSQL → notification → adapter → JSON/SSE → dashboard

1 · Source and generation

The generator reads a source value from the CSV. It applies the selected scenario and vaccine storage profile, calculates measurement uncertainty and status, creates a unique event_id, assigns a shared run_id, creates event_time, and packages the event as JSON.

2 · Transport

The generator publishes the JSON bytes to the MQTT topic devices/temperature. Mosquitto routes that message to the subscriber. Mosquitto does not decide whether the temperature is safe; it transports the message.

3 · Trust and persistence

The subscriber receives the bytes, creates received_at, parses JSON, validates the contract, normalizes values, and derives operational state. It writes the generic and vaccine-specific projections in one transaction, verifies both exist, and commits. PostgreSQL records stored_at when persistence occurs.

4 · Wake-up and read

After commit, PostgreSQL delivers a small notification on cold_chain_events containing the event ID. The adapter receives it, queries PostgreSQL for the complete committed event, maps it into the stable browser contract, and serializes it.

5 · Presentation

The browser initially loaded its HTML, CSS, and JavaScript from port 8766. Its JavaScript either requests JSON from the adapter’s port 8787 API or keeps an SSE connection open at /api/live/stream. It then renders the event as a table row, status card, alert, or chart point.

The three timestamps

  • event_time — event creation at the generator.
  • received_at — arrival at the subscriber.
  • stored_at — database persistence time.

The differences between them help diagnose transport and processing latency.
