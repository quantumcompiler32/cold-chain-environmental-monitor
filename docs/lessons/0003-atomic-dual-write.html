Cold-chain event pipeline · Lesson 3

One event, two database projections

Win for this lesson: you can explain why the subscriber writes both tables in one transaction.

Validated event → telemetry_logs + vaccine_temperature_events → COMMIT → notify dashboard

Why two tables?

telemetry_logs is the generic evidence record: raw JSON payload, topic, device, temperature, and transport timestamps. vaccine_temperature_events is the domain projection: vaccine type, storage bounds, severity, operational status, uncertainty, batch, and dashboard-facing fields.

They represent the same event, joined by the same event_id. The domain table references the generic table, so the domain record cannot exist without its underlying telemetry record.

Why one transaction?

The subscriber opens one PostgreSQL transaction and inserts both projections. If either insert or the consistency check fails, the transaction rolls back. That prevents an event from existing in only one table.

On success, PostgreSQL commits both rows. Only then does pg_notify('cold_chain_events', event_id) become visible to the bridge. The notification means “new committed data exists; look it up,” not “here is the complete event.”

Duplicates are safe

Both inserts use ON CONFLICT (event_id) DO NOTHING. If the same message arrives again, the existing event remains one event. The subscriber reports it as a duplicate rather than creating a second domain row.

Recall
  1. What kind of information belongs in each table?
  2. What could go wrong if the two inserts used separate transactions?
  3. Why is the notification sent only after commit?
