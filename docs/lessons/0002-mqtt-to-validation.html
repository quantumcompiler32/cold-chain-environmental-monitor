Cold-chain event pipeline · Lesson 2

From MQTT message to trusted event

Win for this lesson: you can trace what the subscriber does before any database write occurs.

What MQTT delivers

Mosquitto routes the published bytes to clients subscribed to devices/temperature. The subscriber’s on_message callback receives the topic and payload. At this point, the payload is only text/bytes—not yet a trusted Python event.

MQTT bytes → decode UTF-8 → parse JSON → validate and normalize → derive state → persist

The subscriber’s trust gate

process_message() first records received_at, meaning when this consumer got the message. It decodes the payload and parses JSON. Then validate_event() checks the contract.

  • Required fields exist: identity, device, vaccine, temperature, limits, uncertainty, and status.
  • Types are safe: numbers become floats, timestamps become UTC-aware datetimes, and booleans must really be booleans.
  • event_id must be a UUID, so it can safely identify a database row.
  • The uncertainty fields must agree with the temperature and storage range.
  • Operational state is derived from the normalized event; the subscriber does not blindly trust a sender’s derived status.

Why validate here?

MQTT transports messages; it does not guarantee that the application payload is complete or semantically correct. The subscriber is the boundary that turns “a message arrived” into “this event is acceptable for persistence.” If validation fails, the event is rejected and the database is not written.

Two clocks, so far

event_time answers “when was this simulated reading created?” received_at answers “when did this subscriber receive it?” Their difference is transport/processing delay. Later, PostgreSQL adds stored_at.

Trace exercise

Suppose the payload is valid JSON but is missing measurement_confidence. Does it reach PostgreSQL? Which function rejects it, and why is that better than letting the database discover the problem?

Then explain the difference between event_time and received_at in one sentence.
